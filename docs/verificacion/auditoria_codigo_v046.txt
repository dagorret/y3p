1. Qué se midió y qué significa

Se cuentan archivos de código propio y líneas físicas, incluidos comentarios y
líneas en blanco. Es una medida de tamaño y legibilidad, no de complejidad ni de
líneas ejecutables. Se excluyen .venv, .git, cachés, dependencias y migraciones
con cabecera Generated by Django; también sus inicializadores vacíos. Se incluyen
11 migraciones de datos escritas a mano: contienen reglas institucionales y no
son código autogenerado. Sin ellas, el conteo Python es 110 antes y 111 después.
Las dependencias Tailwind y HTMX por CDN no son JavaScript propio.

                 Antes       Después

.html                35            46
.js                   0             4

Los cuatro JS finales son tres módulos de ejecución y una suite de cinco pruebas.
Las 46 plantillas comprenden 45 del portal y una del administrador técnico.

3. Hallazgos de HTML y JavaScript, y corrección aplicada

Antes: 35 HTML, dos scripts inline y un onclick propio; 95 líneas contenían cuatro
o más etiquetas HTML. La ficha mayor tenía apenas 88 líneas físicas porque sus
paneles estaban comprimidos. Por eso el umbral de 200 líneas aislado ocultaba el
problema de lectura. Las cabeceras estructurales y anclajes no estaban explicados
de manera uniforme.

Después: 46 HTML con cabeceras en castellano, etiquetas #F..., responsabilidad,
anclajes HTMX y permisos de visibilidad. Hay 27 parciales, 11 nuevos. No queda
ningún script propio embebido ni manejador onclick/onchange/onsubmit. Tampoco
quedan líneas con cuatro o más etiquetas HTML. Las tablas tienen cabeceras,
filas y celdas separadas; se usan dos espacios, atributos distribuidos y líneas
en blanco entre bloques. Permanecen algunas líneas largas de texto o clases
utilitarias, pero ninguna grilla compactada. La mayor plantilla tiene 176 líneas
(base_administracion.html); no hay HTML mayor de 200 líneas.

Se separaron barra por lote, tabla, fila, paginación/snippets, tabla Outbox,
actividad Teams y cinco secciones de la Ficha 360°. Se preservan los contratos
#tabla-alumnos-container, #student-filters, #student-query-panel, #query-builder,
#identity-card, #outbox-monitor, #outbox-badge y #teams-panel, las protecciones
CSRF y los enlaces que conservan filtros y ámbito.

Módulos bajo apps/portal/static/portal/js/:
- admin_navigation.js (27 líneas): menú móvil, ARIA, Escape y cambio de ancho.
- student_grid.js (37 líneas): selección, contador y barra por lote; delegación
  de eventos que tolera reemplazos HTMX sin referencias a nodos eliminados.
- student_export.js (14 líneas): filtros actuales del formulario, incluso tras
  reemplazo fuera de banda, trasladados al enlace de Excel.

La base carga cada módulo una sola vez mediante defer. STATIC_URL es /static/;
Django encuentra los módulos mediante la app staticfiles. STATICFILES_DIRS
conserva el directorio raíz si existe. Se verificaron las tres rutas con findstatic.
Los estilos declarativos de bases/ficha siguen en HTML con formato legible;
Tailwind y HTMX siguen externos por CDN. Su empaquetado/CSP pertenece al bloque
productivo pendiente, junto con STATIC_ROOT y entrega web de estáticos.

Formato reproducible: djLint 1.50.0, perfil Django, configuración djlint.toml.
La herramienta se ejecutó temporalmente; no se agregó a dependencias de producción.
El chequeo de formato y git diff --check concluyeron sin diferencias/errores.

7. Cierre del release

El contenido corresponde a v0.4.6 y se prepara en un único commit en la rama de
auditoría, para fusión fast-forward a main, etiqueta anotada y publicación de
main, rama y etiqueta en GitHub y Azure DevOps. Los identificadores definitivos
se verifican después de confirmar este documento para evitar una autorreferencia
de hash dentro del commit.

La firma GPG del commit agotó el tiempo de espera al desbloquear la clave.
Se completa el cierre con commit y etiqueta anotada sin firma criptográfica,
mediante excepciones por comando, sin modificar la configuración de Git.
